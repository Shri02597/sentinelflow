# SentinelFlow — Real-Time E-Commerce Security Monitoring & User Behavior Intelligence Platform

## Overview

**ShopFlow** is a real, working online shop — register, browse, search
products, add to cart, check your order activity. **SentinelFlow** is the
security engine running behind it: every request is logged, analyzed, and
scored in real time, and anything that looks like an attack — brute-force
logins, malicious-looking search input, request floods, endpoint scanning,
or a deviation from a user's own behavioral baseline — becomes a scored
security event on a live analyst dashboard, pushed over WebSockets.

There is no "Attack Simulation" button. The shop's own login form, search
box, and product endpoints *are* the attack surface — suspicious activity is
generated by actually using the application abnormally (see
[Demonstration Flow](#demonstration-flow) below).

## Two Applications, One Backend

| | ShopFlow (the shop) | SentinelFlow (the security layer) |
|---|---|---|
| Audience | `USER` role | `ANALYST` / `ADMIN` roles |
| Visual identity | Light, modern e-commerce UI (`ShopLayout`) | Dark SOC-style dashboard (`SentinelLayout`) |
| Pages | Home, Products, Product Detail, Search, Cart, Profile, Activity | Dashboard, Security Events, Threat Detail, Risky Users, User Risk Profile, (Admin) User Management, Settings |
| Backend routers | `products`, `cart`, `users` (own profile/activity) | `security`, `admin`, `ws` |

Both sides share the same FastAPI backend, JWT auth, and database — the
split is only in routing/RBAC and frontend layout, not infrastructure.

## Architecture

```
User
  → ShopFlow React Frontend (register / login / browse / search / cart)
  → FastAPI Backend
  → Application APIs (auth, products, cart, users)
  → Request Logging Middleware
  → Detection Engine (5 pluggable detectors)
  → Risk Scoring Service
  → SecurityEvent (PostgreSQL / SQLite)
  → WebSocket broadcast (/ws/security)
  → SentinelFlow Analyst Dashboard (live feed, charts, incident management)
```

## Technology Stack

**Frontend:** React, Vite, Tailwind CSS, React Router, Recharts, Axios, native WebSocket client
**Backend:** FastAPI, SQLAlchemy, Pydantic v2, python-jose (JWT), passlib/bcrypt, slowapi (rate limiting)
**Database:** PostgreSQL (production), SQLite (local dev fallback)
**Deployment:** Vercel (frontend), Render/Railway/Fly.io (backend), managed Postgres

## Detection Methodology

| Detector | Trigger | Attack Type |
|---|---|---|
| Brute Force | 5+ failed logins, same IP, rolling 5-min window | `BRUTE_FORCE` |
| Suspicious Input | Predefined SQLi/XSS/path-traversal-like patterns submitted to `/api/products/search` (or other sniffed fields) | `SUSPICIOUS_INPUT` |
| Abnormal Rate | Requests/min from one IP exceeds a configurable ceiling | `ABNORMAL_RATE` |
| Suspicious Endpoint | Repeated 401/403/404s from one IP (scanning/probing signature) | `SUSPICIOUS_ENDPOINT` |
| Behavioral Anomaly | A user's request rate deviates from their own rolling baseline by a configurable multiplier | `BEHAVIORAL_ANOMALY` |

Each detector is a standalone class implementing `Detector.check(db, log) -> dict | None`
(see `backend/app/detectors/`). Adding a new one means writing the class and
registering it in `backend/app/services/detection_engine.py` — nothing else
changes.

> **Note on shared-IP demos:** the abnormal-rate detector counts requests per
> source IP. If you generate a traffic burst and browse the analyst dashboard
> from the *same machine*, the dashboard's own polling can transiently
> inherit some of that IP's elevated risk score. This is expected — in a real
> deployment, analysts and attackers don't share a source IP — and does not
> happen with the other four detectors, which key more precisely (login
> target, exact endpoint, authenticated user).

## Risk Scoring Methodology

Each detection applies a weighted delta (configurable in `app/config.py`,
and live-adjustable by an admin via `/api/admin/settings`) to a running
0–100 score per user (or per IP, for unauthenticated activity):

- Brute force / repeated auth failures: +20
- Abnormal request rate: +25
- Suspicious input: +30
- Suspicious endpoint access: +20
- Behavioral anomaly: +20
- Repeat offense bonus: +5

Levels: `LOW` (0-29), `MEDIUM` (30-59), `HIGH` (60-79), `CRITICAL` (80-100).
The reasons contributing to a score are stored and shown on the User Risk
Profile page (e.g. "6 failed login attempts", "abnormal request rate").

## Response & Containment

Detection alone doesn't stop anything. SentinelFlow closes the loop: once a
subject crosses a risk threshold, the platform **warns** it, and at CRITICAL
**blocks** its traffic outright.

| Trigger | Action | Effect |
|---|---|---|
| Score ≥ 60 (`HIGH`) | `WARN` | Banner in the shop UI. Traffic unaffected. |
| Score ≥ 80 (`CRITICAL`) | `BLOCK` | Every request from the source IP gets `403`. |

Both are configurable in `app/config.py` (`AUTO_WARN_RISK_SCORE`,
`AUTO_BLOCK_RISK_SCORE`, `AUTO_RESPONSE_ENABLED` — set the last one to `False`
for a detect-only deployment).

**Why block the IP and not the account.** A brute-force target is usually the
*victim*, not the attacker. Auto-locking their account would hand the attacker
an account-lockout denial of service. The IP is the thing you can actually cut
off, so blocking is keyed on it; warnings go to the account, when there is one.

**Attribution.** `GET /api/security/threats/top` answers "which IP is the worst
offender and what is it running?" in one row per source — risk score, dominant
attack type, per-attack breakdown, affected accounts, and whether it is already
blocked or warned. Surfaced on the dashboard as **Top Threats**, with inline
Warn/Block controls.

**Analyst actions.** Every threat detail page has a Response panel (warn /
block / release, with a reason). `GET /api/security/response/actions` is an
append-only audit trail of every decision, automatic or manual, so "who blocked
this and why" is always answerable.

**Design constraints worth knowing:**
- `ResponseAction` is append-only; `BlockedIdentity` holds current enforcement
  state so the middleware answers "is this blocked?" with one indexed lookup
  instead of replaying history per request.
- Blocked requests are still written to `request_logs` (as `403`) *before*
  rejection — a blocked host probing the API stays visible to the detectors.
  `EnforcementMiddleware` is registered before `LoggingMiddleware` precisely to
  get this ordering.
- Analysts and admins are never locked out of `/api/security` or `/api/admin`.
  A block you can't inspect or undo isn't a control, it's an outage.

## Network Resilience

The dashboard does not depend on the WebSocket. Every frame it pushes is also
served over REST, so a bad link degrades the feed instead of freezing it.

| Condition | Behaviour |
|---|---|
| Socket live | WebSocket push, no polling at all |
| Socket down, tab visible | REST polling every 15s, socket retrying with jittered backoff |
| Socket down, tab hidden | Polling slows to 60s (nobody's watching a background tab) |
| No network | All retries and polling pause; resume immediately on the `online` event |
| Token rejected (4401/4403) | Retries **stop** — the session is cleared rather than looping forever |

Failures are also isolated per panel: the dashboard fetches stats, traffic and
events with `Promise.allSettled`, so one slow endpoint degrades one card instead
of blanking the page. Live-socket refetches are coalesced to at most one per 2s
so a burst of detections can't cause a request storm on a weak connection.


## Database Schema

- `users` — auth + role (`USER`, `ANALYST`, `ADMIN`)
- `products` — e-commerce catalog (name, description, category, price, image, stock)
- `cart_items` — per-user cart (one row per user/product pair; quantity bumps on repeat add)
- `request_logs` — every request, indexed by IP/user/endpoint + timestamp
- `security_events` — detector output: attack type, severity, risk score, status
- `incidents` / `incident_notes` — analyst investigation trail
- `risk_scores` — current score/level per user or IP
- `response_actions` — append-only WARN/BLOCK/UNBLOCK audit trail
- `blocked_identities` — current enforcement state per target
- `notifications` — warnings delivered to an account

A small demo catalog (12 products across Electronics/Furniture/Lifestyle/
Kitchen/Apparel) is seeded automatically on first startup if the table is
empty (`app/services/seed.py`).

## Security Considerations

- Passwords are bcrypt-hashed; plaintext is never logged or stored.
- Sensitive request bodies (passwords) are never persisted in `RequestLog`.
- The suspicious-input detector only inspects a value transiently, per-request,
  and never writes the raw payload to the database.
- All detection and "attack simulation" targets this application's own
  endpoints only — there is no offensive/attack tooling anywhere in this
  codebase, and nothing here can be pointed at an external target.
- JWT access tokens are short-lived; refresh tokens are longer-lived and
  should be rotated in a production hardening pass.
- RBAC is enforced on the backend (`require_roles` dependency) on every
  protected route — the frontend's route-level gating is a UX convenience,
  not the security boundary.

## Demonstration Flow

1. Open ShopFlow, register a user, log in.
2. Browse `/products`, search for something, add an item to `/cart`.
3. Open `/security` (log in as an `ANALYST`/`ADMIN` account) in another tab —
   the SentinelFlow dashboard, visually distinct from the shop.
4. Generate controlled suspicious activity through ShopFlow's own interfaces:
   - **Brute force**: on the login page, enter a real registered email with
     6+ wrong passwords.
   - **Suspicious input**: search products for a predefined test string like
     `' OR 1=1 --`.
   - **Abnormal rate**: refresh/browse `/products` rapidly (100+ requests/min).
   - **Suspicious endpoint**: request a few nonexistent URLs.
5. Watch the SentinelFlow dashboard update live via WebSocket — no refresh.
6. On the **Top Threats** panel, the offending IP is already ranked with its
   dominant attack type. Press **Warn**, then **Block IP** — or wait for the
   auto-response policy to do it once the score hits 80. Requests from that IP
   start returning 403 while the console stays usable.
7. Open the event's Threat Detail page, review the related request timeline,
   change status to `INVESTIGATING` then `RESOLVED`, and use the Response
   panel to release the block.
8. As the warned shopper, a security banner appears in the ShopFlow header
   area explaining the warning.
9. `/security/containment` shows the live block list and the full audit trail
   of every automatic and manual action.
10. As an `ADMIN`, visit `/admin/users` to manage roles, or `/admin/settings`
    to adjust detection thresholds live.
